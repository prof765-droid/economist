# Economist — ипотечный калькулятор

[![CI](https://github.com/prof765-droid/economist/actions/workflows/ci.yml/badge.svg)](https://github.com/prof765-droid/economist/actions/workflows/ci.yml)

Pet-проект на Symfony + React. Идея простая, смысл проекта в качестве реализации: точная денежная арифметика, слоистая архитектура с автоматической проверкой границ, тесты и CI.

**Что умеет:**
- считать ипотеку по стоимости жилья, первоначальному взносу, ставке, сроку (в годах или месяцах) и дате выдачи;
- два типа погашения — **аннуитетный** (платёж одинаковый) и **дифференцированный** (долг гасится равными частями, платёж уменьшается);
- показывать итоги (сумма кредита, ежемесячный платёж, всего выплат, переплата) и помесячный график;
- делиться расчётом по ссылке `/c/{uuid}` без регистрации: кнопка «Поделиться» сохраняет расчёт и выдаёт ссылку.

**Чего нет, и это сознательно:** досрочных погашений, авторизации, деплоя, процентов по фактическим дням, учёта выходных.

## Запуск

Нужны только Docker с Compose v2 и `make`. PHP, Node и PostgreSQL на хост ставить не нужно, всё работает в контейнерах.

```bash
git clone https://github.com/prof765-droid/economist.git
cd economist

make build     # образ PHP, composer install, npm ci, миграции dev-БД
make up        # запустить контейнеры
```

После этого:

| Адрес | Что там |
|---|---|
| http://localhost:8080 | калькулятор |
| http://localhost:8080/api/doc | Swagger UI — документация API, можно отправлять запросы прямо со страницы |
| http://localhost:8080/api/doc.json | схема OpenAPI в JSON |

Тесты и линтеры:

```bash
make test-db   # один раз: создать тестовую БД и применить к ней миграции
make test      # PHPUnit + Vitest
make lint      # PHP-CS-Fixer, PHPStan, Deptrac, lint:container, oxlint, tsc
make down      # остановить контейнеры
```

У каждой цели есть половинки `-backend` и `-frontend`: например, `make up-backend` поднимает только API (на `/` тогда честный `502`), `make test-frontend` запускает только Vitest. Полный список целей — в [`Makefile`](Makefile).

**Почему подготовка и запуск — две команды.** Каталог `backend/` подключён в контейнер bind mount'ом. Пакеты, поставленные при сборке образа, оказались бы под ним скрыты, поэтому `composer install` идёт отдельным шагом. Таблицы создают миграции, а при сборке образа PostgreSQL ещё не запущен. `make build` нужен после `git clone`, `git pull` или правки `Dockerfile`, повторять его безопасно: он догоняет окружение до кода. `make up` в сеть не ходит и схему БД не трогает, поэтому старт быстрый и предсказуемый.

Секреты не нужны: в репозитории лежит `.env` только с dev-значениями. Swagger UI доступен в окружениях `dev` и `test`, в prod пакеты документации не ставятся.

## Архитектура

```
Браузер ──▶ nginx :8080 ──┬── /       ──▶ React SPA (Vite dev server)
                          └── /api/*  ──▶ php-fpm (Symfony) ──▶ PostgreSQL
```

Фронт и API живут на одном домене за nginx, поэтому CORS не нужен. Это монорепозиторий: `backend/`, `frontend/`, `docker/`.

### Слои бэкенда

Из DDD взяты только тактические паттерны, которые решают реальные задачи проекта: четыре слоя, value objects, сущность, интерфейс репозитория в домене и доменные исключения. Агрегаты, доменные события, CQRS и шина команд для трёх сценариев и одной сущности оказались бы лишними.

```
backend/src/
├── Domain/Mortgage/          бизнес-правила, чистый PHP
│   ├── Money.php
│   ├── Credit/               условия кредита: CreditTerms, InterestRate, RepaymentType
│   ├── Schedule/             результат: Payment, PaymentSchedule
│   ├── Calculator/           как считать: стратегии аннуитета и дифференцированного
│   └── Calculation/          сохранённый расчёт: сущность и интерфейс репозитория
├── Application/Mortgage/     сценарии: CalculateMortgage, SaveCalculation, GetCalculation
├── Infrastructure/Persistence/   DBAL-репозиторий и маппер строки БД ⇄ объект
└── UI/Http/                  контроллеры, Request/Response DTO, ExceptionListener
```

Внутри домена классы сгруппированы по понятиям предметной области (`Credit/`, `Schedule/`), а не по типам (`Entity/`, `Service/`): связанный код лежит рядом.

**Правило зависимостей** — стрелки только внутрь, к домену:

```
              ┌──────────┐
              │    UI    │──── Symfony
              └────┬─────┘
          ┌────────┴───────┐
          ▼                │
   ┌─────────────┐         │
   │ Application │         │
   └──────┬──────┘         │
          ▼                ▼
        ┌────────────────────┐        ┌────────────────┐
        │       Domain       │◀───────│ Infrastructure │──── Doctrine DBAL, Symfony
        └────────────────────┘        └────────────────┘
          brick/math, symfony/uid — разрешены всем слоям
```

| Слой | Отвечает за | Чего в нём нет |
|---|---|---|
| **Domain** | деньги, ставка, инварианты, расчёт графика | фреймворка, HTTP, SQL |
| **Application** | сценарии «рассчитать», «сохранить», «получить» | бизнес-правил и Symfony |
| **Infrastructure** | БД через Doctrine DBAL | решений о том, *что* делать |
| **UI** | точки входа: HTTP-запрос → команда сценария → JSON-ответ | бизнес-логики |

`UI` здесь — не интерфейс с кнопками (он во `frontend/`), а слой «User Interface» в терминах Эванса: любая точка, через которую внешний мир обращается к приложению. Сейчас это HTTP-контроллеры.

Домен объявляет интерфейс `CalculationRepository`, а Infrastructure его реализует (Dependency Inversion). Domain и Application не зависят от способа хранения: SQL и маппинг целиком в Infrastructure.

### Deptrac: границы проверяет CI

Правила слоёв без автоматической проверки остаются благими намерениями: IDE молча подставит `use Symfony\...` в доменный класс. [Deptrac](backend/deptrac.yaml) смотрит, от кого зависит каждый класс (`use`, `new`, типы в сигнатурах), и роняет CI при нарушении.

Важная деталь: Deptrac проверяет зависимости только между *описанными* слоями. Поэтому внешние библиотеки (Symfony, Doctrine, `brick/math`, PSR Clock, OpenAPI) тоже описаны слоями, правила записаны белым списком, а в CI стоит `--fail-on-uncovered`. Новая библиотека без слоя роняет сборку: приходится осознанно решить, каким слоям она доступна. Домену разрешены только `brick/math` (по сути, расширение языка) и `symfony/uid` (самостоятельный компонент без фреймворка).

## Ключевые решения

### Деньги — точно в трёх слоях

| Слой | Тип | Пример |
|---|---|---|
| БД | `NUMERIC(15, 2)`, ставка — `NUMERIC(5, 2)` | `3500000.00` |
| PHP | `BigDecimal`, обёрнутый в value object `Money` | `Money::of('3500000.00')` |
| JSON | строка | `"3500000.00"` |

- `float` нигде не участвует. В JSON деньги идут строкой, потому что число в JavaScript — это `float`. Фронт ничего не считает, только показывает.
- **Точность value object равна точности колонки.** PostgreSQL молча округляет лишние знаки при записи в `NUMERIC(p, 2)`. Поэтому домен сам округляет деньги и ставку до 2 знаков (`HALF_UP`) ещё при создании объекта. Иначе расчёт со ставкой `18.555` и тот же расчёт, открытый по ссылке (в БД уже `18.56`), дали бы разные графики.
- Фронт проверяет суммы в копейках через `BigInt`. На `float` выражение `1000000.07 − 500000.07` даёт `499999.99999999994`, и форма отвергла бы допустимую сумму кредита ровно 500 000.

### DBAL без ORM

У проекта одна таблица без связей, запись идёт один раз, чтение — по id. Возможности ORM (отслеживание изменений, identity map, связи, lazy loading) здесь не нужны, а его ограничения (создание объектов в обход конструктора, прокси, метаданные маппинга на сущности) остались бы. Репозиторий работает через `Connection`, а ручной `CalculationMapper` переводит строку БД ⇄ доменный объект. Домен о базе данных не знает вообще. Цена решения: миграции пишутся на SQL вручную (`doctrine:migrations:diff` работает от метаданных ORM), маппинг восьми полей тоже ручной.

### Command + прямой вызов handler'а, без шины

Контроллер собирает из Request DTO команду (`final readonly` класс со скалярами) и вызывает handler напрямую. Сценарии синхронные, middleware не нужны, поэтому шина команд дала бы только лишний уровень косвенности. Команды и handler'ы устроены так же, как в шине:
- команды — чистые данные, без сервисов внутри;
- на каждый сценарий отдельный handler с `handle()`, а не общий `MortgageService`;
- UUID расчёта генерирует контроллер, так что handler сохранения ничего не возвращает — так работают команды в шине.

**Почему handler не принимает Request DTO напрямую.** Тогда Application зависел бы от UI, и стрелка смотрела бы наружу. Request — это «что пришло снаружи, ещё не проверено», с nullable-полями и атрибутами `#[Assert]`. Command — «намерение, готовое к исполнению», с non-null полями и без Symfony.

**Валидация — в два уровня без пересечений.** Symfony Validator на Request DTO проверяет формат: поле есть, это число, дата разбирается. Бизнес-правила проверяет домен в `CreditTerms::create()`: лимиты и точность. Нарушения собираются все сразу, и фронт получает одинаковый `422` от обоих уровней.

### Два POST-эндпоинта вместо одного с флагом

`POST /api/mortgage/calculate` считает и ничего не сохраняет. `POST /api/calculations` сохраняет и вызывается только кнопкой «Поделиться». Пользователь перебирает много вариантов, а в БД должно попадать только то, чем делятся. Почему не один эндпоинт с флагом `save: true`:
- у операций разная семантика HTTP: `200` с графиком против `201` с `Location`;
- rate limiter вешается на маршрут конфигом, а с флагом проверка безопасности зависела бы от данных, присланных клиентом;
- булев параметр, переключающий поведение, — признак функции, которая делает две вещи.

Оба эндпоинта принимают один и тот же `CalculateMortgageRequest`, так что поля и правила валидации описаны один раз. Лимит записи — 30 запросов в минуту с IP, лимит расчёта мягче — 60.

### Храним только входные параметры

В таблице `calculation` лежат только параметры кредита и время создания. График пересчитывается при каждом `GET`: расчёт детерминирован, источник правды один. При сохранении фронт присылает параметры, а не результат, потому что бэкенд не доверяет вычислениям клиента. При чтении маппер восстанавливает объект через тот же `CreditTerms::create()`, поэтому в БД может лежать только то, что прошло инварианты.

### Ошибки — RFC 9457 Problem Details

Все ошибки отдаются в формате `application/problem+json`. `ExceptionListener` переводит в ответ два доменных исключения — неверные условия кредита (`422`) и расчёт не найден (`404`) — и HTTP-исключения Symfony. Любое другое исключение — это баг: `500` без деталей и запись в лог. Ошибки ввода пользователя логируются на уровне `info`, чтобы буфер `fingers_crossed` в prod не сбрасывался на каждую опечатку в форме.

### Документация API из кода

Swagger UI (`/api/doc`) строится `nelmio/api-doc-bundle` по маршрутам и DTO. Схема ошибок берётся из настоящего класса `ProblemDetails`, из которого `ExceptionListener` собирает ответ. Поменяется формат, поменяется и документация, расходиться им нечему. Вручную написанный `openapi.yaml` устарел бы при первой же правке DTO.

## Как считается график

### Лимиты

| Параметр | Ограничение | Почему |
|---|---|---|
| Сумма кредита (стоимость − взнос) | ≥ 500 000.00 ₽ | ипотека — это заём, и ограничивается именно он. Нарушение подсвечивается на поле взноса: исправить его можно, уменьшив взнос |
| Стоимость | ≤ 10 000 000 000.00 ₽ | чтобы большое число вернуло понятный `422`, а не ошибку БД `500` |
| Ставка | больше 0 и не больше 30 % | выше реальных ипотечных ставок |
| Срок | 1–360 месяцев | 30 лет — максимум в российских банках |

### Округление — как в банке

Заплатить дробную копейку нельзя, поэтому проценты каждый месяц округляются до копейки (`HALF_UP`), и остаток долга уменьшается на округлённую сумму. Месячная ставка `ставка / 12 / 100` хранится с 10 знаками и до копеек не округляется.

**Аннуитет:** платёж `A = ROUND(S · i / (1 − (1 + i)^−n), 2)` считается один раз. Каждый месяц проценты равны `ROUND(остаток · i, 2)`, а в долг уходит `A − проценты`.

**Дифференцированный:** основной долг `ROUND(S / n, 2)` одинаков каждый месяц, проценты начисляются на остаток.

**Последний платёж корректируется**, чтобы остаток стал ровно `0.00`: в него уходит накопленная разница округлений. Поэтому последний аннуитетный платёж может отличаться от остальных на копейки, а у дифференцированного при малой ставке бывает чуть больше предпоследнего.

**Правило `min` — страховка.** В долг каждый месяц уходит не больше остатка: `min(плановое погашение, остаток)`. Ошибки округления растут как сложные проценты, и при более мягких лимитах долг иногда кончался бы раньше срока. Без `min` остаток ушёл бы в минус, и корректный ввод получил бы `500`. При текущих лимитах такое невозможно: в худшем случае (500 000 ₽, 30 %, 360 мес.) накопленная ошибка в 4 раза меньше последнего погашения. Поэтому правило через валидный ввод не тестируется, но позволяет менять лимиты, не пересчитывая заново, сойдётся ли график.

**Почему не сверяемся с `IPMT` из Excel.** `IPMT` считает дробными копейками без промежуточного округления. На длинном сроке расхождение с реальным графиком копится до рублей, и такого графика не выдаст ни один банк. Эталон регулярного аннуитетного платежа — `ROUND(PMT(...); 2)`, короткие графики посчитаны вручную, арифметика записана в комментариях тестов.

### Даты платежей

- Платёж № N приходится на дату выдачи + N месяцев. Дата считается от даты выдачи, а не от предыдущего платежа, иначе после февраля график «съехал» бы: 31 → 28 → 28 → 28…
- Если такого числа в месяце нет, платёж приходится на последний день месяца: 31 января → 28 (29) февраля → 31 марта → 30 апреля.
- Ловушка PHP: `modify('+1 month')` от 31 января даёт 3 марта, поэтому день вычисляется явно.

### Сознательные упрощения

- Проценты начисляются помесячно (ставка / 12), а не по фактическому числу дней.
- Дата платежа — то же число месяца без переноса с выходных.
- `monthlyPayment` в итогах — первый платёж. У аннуитета это регулярный платёж, у дифференцированного — максимальный.

## API

| Метод и путь | Что делает | Ответ |
|---|---|---|
| `POST /api/mortgage/calculate` | расчёт без сохранения | `200` |
| `POST /api/calculations` | сохранить параметры («Поделиться») | `201` + `Location` + `{ "id" }` |
| `GET /api/calculations/{id}` | получить сохранённый расчёт | `200` / `404` |

Полное описание схем — в Swagger UI на http://localhost:8080/api/doc.

### Расчёт

Запрос (одинаковый для обоих `POST`; срок в API — в месяцах, ключи — camelCase):

```bash
curl -X POST http://localhost:8080/api/mortgage/calculate \
  -H 'Content-Type: application/json' \
  -d '{
    "propertyPrice": "5000000.00",
    "downPayment": "1000000.00",
    "annualRate": "18.5",
    "termMonths": 3,
    "repaymentType": "annuity",
    "startDate": "2026-01-31"
  }'
```

Ответ `200` (заодно видно правило дат и корректировку последнего платежа на копейку):

```json
{
  "summary": {
    "creditAmount": "4000000.00",
    "monthlyPayment": "1374654.09",
    "totalPayment": "4123962.28",
    "overpayment": "123962.28"
  },
  "schedule": [
    { "number": 1, "date": "2026-02-28", "payment": "1374654.09", "interest": "61666.67", "principal": "1312987.42", "balance": "2687012.58" },
    { "number": 2, "date": "2026-03-31", "payment": "1374654.09", "interest": "41424.78", "principal": "1333229.31", "balance": "1353783.27" },
    { "number": 3, "date": "2026-04-30", "payment": "1374654.10", "interest": "20870.83", "principal": "1353783.27", "balance": "0.00" }
  ]
}
```

`repaymentType` принимает значения `annuity` или `differentiated`.

### Сохранение и получение

```
POST /api/calculations           (тело как у расчёта)

HTTP/1.1 201 Created
Location: /api/calculations/01a1976b-3c55-7913-afe9-277d4dbc80da

{ "id": "01a1976b-3c55-7913-afe9-277d4dbc80da" }
```

`GET /api/calculations/{id}` возвращает те же `summary` и `schedule`, что и расчёт, а также `id` и `parameters` в формате запроса. По ним кнопка «Открыть в калькуляторе» заполняет форму. Невалидный UUID в адресе даёт `404`: для клиента ресурса по такому адресу просто нет.

### Ошибки

```json
{
  "type": "https://economist.local/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "violations": [
    { "field": "annualRate", "message": "Ставка должна быть больше 0 % и не больше 30 %" },
    { "field": "downPayment", "message": "Сумма кредита должна быть не меньше 500 000 ₽" }
  ]
}
```

| Код | Когда |
|---|---|
| `400` | невалидный JSON |
| `422` | ошибка формата поля или нарушение бизнес-правила; все нарушения сразу |
| `404` | расчёт не найден или некорректный UUID |
| `429` | превышен лимит запросов, есть заголовок `Retry-After` |
| `500` | непредвиденная ошибка, без деталей в ответе |

## Тесты и CI

**Бэкенд (PHPUnit):**
- unit-тесты домена — основная масса: эталонные значения из независимого расчёта (`PMT`, ручные короткие графики), инварианты на длинных сроках (сумма погашений равна сумме кредита, остаток ровно `0.00`, платежи не растут), края лимитов (499 999.99 / 500 000.00, 30 / 30.01 %), даты (31-е число, 29 февраля);
- интеграционный тест репозитория на настоящем PostgreSQL: круг save → find сохраняет точность `NUMERIC`;
- функциональные тесты API: коды `200/201/404/422/429`, формат Problem Details, `GET` сохранённого расчёта совпадает с `calculate`, схема `/api/doc.json`.

**Фронт (Vitest + React Testing Library):** валидация формы, перевод срока из лет в месяцы, подсветка полей из `422`, рендер графика, «Поделиться». API в этих тестах мокается.

**CI** ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) на каждый push и pull request запускает два параллельных job'а:

| backend | frontend |
|---|---|
| `composer validate`, `composer audit` | `npm ci`, `npm audit` |
| PHP-CS-Fixer `--dry-run` | oxlint |
| PHPStan `max` | `tsc -b` |
| Deptrac `--fail-on-uncovered`, `lint:container` | Vitest |
| миграции + PHPUnit на сервисе `postgres:18` | `vite build` |

Dependabot присылает PR с обновлениями зависимостей.
